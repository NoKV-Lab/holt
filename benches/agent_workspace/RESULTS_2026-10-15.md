# Holt 与 SQLite：agent workspace 本地端到端工作流

测量日期：2026-10-15。结论：Holt 的多 Tree 一致性读取和 COW/回收成本确实明显；但整体吞吐的胜负还取决于持久化和 checkpoint 策略，不能用 SQLite `synchronous=OFF` 的结果替代生产配置的结论。

## 测量边界

这是同一个应用 handler、两种存储适配器的工作流比较：

```text
JSON 请求编解码 → workspace 领域逻辑 → 多 Tree/多表读写事务
              → 可选的本地内容文件读写与 CRC 校验 → JSON 响应编解码
```

不包含 NoKV SDK/RPC、网络或远端对象服务，也不包含故障注入、断电验证或无限期保留测试。它不能被称为完整 NoKV 产品的性能结果。

- Holt：本地 `0.9.2` 源码，commit `f080daf2bc9d8019bb134141dc5ee31fd36f2c03`。本轮未改引擎实现。
- SQLite：rusqlite `0.39.0`，bundled SQLite `3.51.3`。
- 硬件：Apple M3 Pro，12 logical CPUs，36 GiB RAM；macOS 26.6.2（Darwin 25.6.0），Apple ARM64。
- 编译：Rust `1.97.1`，release，opt-level 3，thin LTO，codegen-units 1；两边在同一个可执行文件中。
- 初始数据：8 个 workspace，每个 512 个文件，共 4,096 个路径。
- 元数据族：workspace、path、revision、object_ref、operation、dedupe、history、event。Holt 为 8 棵 named Tree，SQLite 为 8 张 `WITHOUT ROWID` 表；值的编码相同。
- 混合操作：40% read、15% stat、15% list（最多 64 条，返回名称及元数据）、20% publish、5% rename roundtrip、3% remove+recreate、2% 全 8 族一致性 snapshot。实际计数随固定 seed 采样，原始数据逐项保留。
- publish 一次原子更新 8 个元数据族。rename roundtrip 与 remove+recreate 分别包含两次提交。历史、receipt 和 immutable revision/content 保留；未运行 vacuum。
- 4 客户端各自使用不同 workspace，共享同一个 DB 和元数据族。全部测量的 CAS retry 均为 0。
- Holt 的 cache target 为共享 64 MiB；SQLite 为每连接 64 MiB。它们不等于相同的总内存限制：本次 SQLite 最大 RSS 小于 20 MiB，Holt 的受保护 dirty/COW 帧则能远超 cache target。下表另报实际峰值 RSS。

每个场景运行 8 个独立进程，顺序为 H,S,S,H / S,H,H,S，每引擎 4 次。下面是每进程指标的中位数；p95 也是 4 个进程 p95 的中位数，不是池化分位数。共 128 次正式运行全部通过完整有序领域数据校验、跨引擎/重复运行一致性检查和关闭重开检查；另有不计入统计的 smoke/runner QA。

## 持久化配置

必须分开看这些行：

| Profile | Holt | SQLite | 用途与限制 |
|---|---|---|---|
| 异步诊断 OFF | WAL `sync=false` | WAL `synchronous=OFF` | 两者无逐操作同步，但 buffering 和 crash consistency 不相同；不作为严格持久性等价比较。 |
| 周期 checkpoint / NORMAL | WAL `sync=false`，默认后台 checkpoint 开启 | WAL `NORMAL`，autocheckpoint=1000 pages | Holt 默认 500 ms/512 dirty blobs，SQLite 为 1000 WAL pages；同步周期和每轮字节数不同，按各自策略报告。 |
| 同步 FULL | WAL `sync=true` | WAL `FULL` | SQLite 同时开启 `fullfsync=ON` 和 `checkpoint_fullfsync=ON`，与此 macOS Rust `File::sync_data()` 的 `F_FULLFSYNC` 路径对齐。 |

4 KiB 内容的同步发布在两边都同步内容文件和父目录。基准未做断电证明。每个 burst 都有最终显式 durable checkpoint，耗时单独报告，也保留包含该 drain 的吞吐。

attached 场景还将相同结构的 canonical mutation 与领域数据同事务保存：Holt 使用 attached WAL envelope，SQLite 使用事务内 recovery table。最终 checkpoint 退休这些本地恢复材料。它不是共享日志、远程复制或永久审计日志的比较。

## 更接近实际服务配置的结果

| 工作流 | 客户端 | 请求数/进程 | Holt ops/s | SQLite ops/s | H/S | Holt p95 | SQLite p95 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 纯元数据，后台 checkpoint / NORMAL | 4 | 4,000 | 1,975 | 1,558 | 1.27× | 7.39 ms | 9.26 ms |
| 4 KiB 内容，后台 checkpoint / NORMAL | 4 | 4,000 | 1,755 | 1,680 | 1.04× | 4.68 ms | 7.53 ms |
| 纯元数据，同步 FULL，清理后复测 | 1 | 4,000 | 698 | 656 | 1.06× | 6.28 ms | 7.21 ms |
| 4 KiB 内容，同步 FULL，清理后复测 | 1 | 1,600 | 400 | 313 | 1.28× | 9.10 ms | 11.67 ms |
| canonical recovery + 4 KiB 内容，同步 FULL | 1 | 1,600 | 429 | 315 | 1.36× | 9.09 ms | 11.53 ms |

Holt 在这些混合工作流中没有普遍输给 SQLite。4 客户端含内容的 NORMAL 行只有约 4% 差距，低于本机跨进程波动，按接近处理。

同步测试对设备状态敏感。第一组在大体积 COW 压力组之后，普通纯元数据 FULL 的中位数为 H 553 / S 753 ops/s，普通内容 FULL 为 H 323 / S 366；恢复磁盘可用空间后，另做完整平衡顺序复测得到上表。两组均保留，不用单个同步数字宣称可移植排名，也不能把 ordinary 与 attached 不同时间窗口的差异解释成 attached 本身加速。

## 多 Tree 读取成本被总吞吐掩盖

单客户端、纯元数据、异步 OFF 诊断中，整个 mix 是 H 20,124 / S 16,216 ops/s；但逐操作分布不同：

| 操作 | Holt p50 | SQLite p50 |
|---|---:|---:|
| read：3 族一致性读 | 37.7 µs | 4.0 µs |
| stat：3 族一致性读 | 37.9 µs | 4.0 µs |
| list：2 族一致性读、64 条 | 73.3 µs | 47.8 µs |
| snapshot：8 族、每族最多 32 条 | 155.0 µs | 73.3 µs |
| publish：8 族原子提交 | 37.0 µs | 134.3 µs |

这组负载里，Holt 的便宜写入拉高了混合吞吐，同时一致性 point read 约慢 9–10 倍。原始 stage timer 的 H view+reads 为约 492 ms，apply 为约 52 ms；S 分别为约 113 ms 与 568 ms。stage timer 含捕获、等待、实际读取/回调和释放，不能进一步当成纯锁时间或纯 memcpy 时间。

诊断中仅将 read/stat 改成独立 point lookup 后，H 的整个 mix 从 20,124 升到 33,571 ops/s，p50 约 2.2 µs；S 是 16,299 ops/s。其余操作仍使用原来的事务/视图。这个诊断弱化了跨 Tree 一致性，不能作为可直接发布的优化。

## 并发 COW、内存和空间放大

| 场景 | H ops/s | H 峰值 RSS 中位数 | H checkpoint 后元数据分配空间 | H orphan backlog 中位数 |
|---|---:|---:|---:|---:|
| 4 客户端，4,000 请求，关闭后台 checkpoint | 1,000 | 1,391 MiB | 1,323 MiB | 1,071 |
| 4 客户端，12,000 请求，关闭后台 checkpoint | 230 | 6,639 MiB | 8,372 MiB | 8,062 |
| 4 客户端，4,000 请求，后台 checkpoint / NORMAL 对照 | 1,975 | 454 MiB | 1,421 MiB | 936 |
| 4 客户端，4 KiB 内容，后台 checkpoint / NORMAL 对照 | 1,755 | 385 MiB | 1,047 MiB | 750 |

以上分配空间不含内容文件，也不是领域数据净大小。NORMAL 对照中，SQLite 对应峰值 RSS 约 11 MiB、元数据文件约 2.8–3.1 MiB。Holt 长压力组最高单次 RSS 约 8 GiB。压力组最终业务可达拓扑约 30 个 blobs，store 则还保留数千个待回收槽位。

关闭后台 checkpoint 的 OFF 对照中，SQLite 4,000 请求约 14,960 ops/s，12,000 请求约 14,776 ops/s；开启自动 checkpoint 但仍为 OFF 时，SQLite 约 20,950 ops/s。这些数字比 NORMAL 高很多，证明持久性/同步策略是决定性变量，不能拿 OFF 行宣称生产 SQLite 比 Holt 快 10–60 倍。

后台 checkpoint 明显降低了 Holt 内存压力并改善吞吐，但没有消除固定粒度 COW 和回收积压。它也不等于物理文件立刻缩小。这里观察的是一次有界 burst 和最终 checkpoint，不是永久泄漏证明，也不是所有维护收敛后稳态容量。

## 与代码路径的联系及优化顺序

当前 `DB::view` 为每个 scope 分配、复制完整 512 KiB root。一次 read/stat 捕获 3 族，光 root memcpy 就是 1.5 MiB，当前还有完整清零、epoch 注册及 live-root dirty publication。它与 SQLite 建立 read transaction 的成本差异一致。

并发 view 存活时，512 KiB child frame COW 与 dirty/orphan 保护会让 cache target 失去硬上限；当前全 DB fork barrier 还会保守影响未捕获 Tree。即使改成 per-Tree barrier，同一 metadata family 内不同 workspace 仍可能共享一个物理 frame，因此它只会消除一部分保守 fork。

基于本次结果，优先级是：

1. 先降低 DBView 的 root capture 成本，保留一致性与 escaped-view lifetime 语义。
2. 缩小 snapshot/COW domain，完善 dirty/orphan 的有界回收、内存背压和观测。
3. 再缩短 atomic 持 gate 的窗口、批量处理 delta flush、复用 tree resolution。单客户端 async 的 apply 已很便宜，不能预期仅削减 batch 包装就解决并发放大。
4. 后续再评估 immutable root descriptor、较小 COW 单元或版本化读。point-read 诊断给出的是方向和上限，不是正确性等价的替代方案。

本轮没有修改 Holt 的 atomic/view/COW 实现。
